1. RINGKASAN
------------------------------------------------------------------------------------------------

  Target yang diminta: Tartila Press 10.000 pengguna per hari dan Tartila Book 1.000.000 pengguna
  per hari, diakses bersamaan, dengan data yang sudah banyak.

  Kesimpulan:
  +----+---------------------------------------------------------------------------------------+
  | 1  | Tartila Press (10.000 pengguna/hari) RINGAN: puncak sekitar 30 request/dtk, biaya     |
  |    | sekitar 15 ms CPU per request = kurang dari 1 core. Tidak menjadi penentu spesifikasi.|
  | 2  | Tartila Book (1 juta pengguna/hari) adalah beban utama: perkiraan puncak 1.500-3.000  |
  |    | request/dtk dan 15.000-30.000 pembaca bersamaan. Dengan kode sekarang butuh sekitar   |
  |    | 50-90 vCPU, TIDAK mungkin di satu VPS biasa.                                          |
  | 3  | Dengan 4 perubahan arsitektur (bagian 6) kebutuhan turun menjadi sekitar 8-16 vCPU:   |
  |    | satu VPS 16 vCPU / 32 GB RAM / 500 GB NVMe + CDN untuk PDF, atau dipisah app + DB.    |
  | 4  | Untuk Tartila Press saja ditambah Tartila Book sampai sekitar 20.000 pengguna/hari:   |
  |    | VPS 4 vCPU / 8 GB RAM / 160 GB SSD sudah cukup.                                       |
  | 5  | Uji menemukan 5 masalah skala NYATA di kode; 4 sudah diperbaiki (bagian 4), 1 terbuka |
  |    | (laporan Keuangan/Ringkasan admin Press gagal pada +/- 25.000 pesanan lunas).          |
  +----+---------------------------------------------------------------------------------------+

  BATASAN PENTING: angka kapasitas untuk 1 juta pengguna adalah EKSTRAPOLASI dari biaya CPU per
  request yang DIUKUR, bukan hasil uji dengan 1 juta pengguna sungguhan. Mesin uji = laptop
  Windows (4 core / 8 thread), bukan Linux + Nginx + PHP-FPM; di Linux biaya per request biasanya
  lebih rendah, jadi angka di sini cenderung KONSERVATIF. Ulangi uji di VPS staging sebelum membeli
  spesifikasi final (cara di bagian 9).


2. LINGKUNGAN & METODE
------------------------------------------------------------------------------------------------

  Mesin uji   : Intel i7-7700HQ (4 core, 8 thread), 12 GB RAM, Windows 11, PHP 8.2.12, MariaDB 10.4.
  Server web  : Apache + mod_php (48 thread = setara pm.max_children 48), OPcache aktif tanpa JIT,
                validate_timestamps=0, route/config/event cache, APP_DEBUG=false, BCRYPT_ROUNDS=12.
  Database    : MariaDB 10.4, buffer pool 3 GB, innodb_flush_log_at_trx_commit=1 (sama dengan
                produksi), koneksi PHP persisten. CACHE_STORE/SESSION/QUEUE = database (sama dengan
                template produksi deploy/backend.env.example).
  Data uji    : 1.100.000 pengguna (100.000 Press + 1.000.000 pembaca), 5.000 buku, 20.000 naskah,
                60.000 pesanan Press, 300.000 notifikasi; 3.000 buku Tartila Book, 400.000 pesanan
                Tartila Book, 3 juta suka, 3 juta simpan, 600 ribu komentar, 1,5 juta penanda, 3,9
                juta progres baca, 19,8 juta bacaan-halaman (kira-kira satu hari ramai). Total 6,1 GB.
                Buku populer di id kecil (sebaran miring) supaya baris panas ikut teruji.
  Pembangkit  : loadtest.mjs (Node): sesi pengguna datang menurut proses Poisson; tiap sesi menjalankan
                langkah seperti peramban (grup request paralel + waktu berpikir). Waktu berpikir
                dipercepat x0,1 supaya beban tinggi bisa dicapai (biaya per request tidak berubah).
  Sesi Press  : Beranda (9 request paralel) -> katalog (4) -> cari -> detail buku (2); 30% pengguna
                masuk: login, ringkasan, pesanan, naskah, dompet, royalti.
  Sesi Book   : (15% login) katalog+rak (4) -> detail (2) -> buka PDF (3, Range) -> rata-rata 12 halaman,
                tiap halaman: POST /reads + PUT /progress (+ Range tiap 4 halaman) -> kadang suka/simpan/
                penanda/komentar. Rata-rata 36 request per sesi, sesi sekitar 5 menit pada kecepatan nyata.
  Admin       : sesi pemantauan (pesanan, buku, royalti, pesanan Tartila Book).
  Ukuran      : latensi p50/p95/p99, error (5xx, 429, timeout), CPU server (Apache/PHP + MariaDB),
                memori, Mbps, serta profil query per request (qprofile.php).

8. HASIL LAIN
------------------------------------------------------------------------------------------------

  - Login (bcrypt cost 12) rata-rata 31-48 ms; 15-30% sesi memulai dengan login (token bertahan).
  - Press GET /editors hanya untuk pengguna masuk (401 untuk tamu) - sesuai desain.
  - Kunci baris InnoDB: ~4.600 tunggu selama seluruh uji, maks 39 ms; tidak ada antrean kunci
    berkepanjangan setelah perbaikan T3.
  - Memori Apache/PHP 270-295 MB untuk 48 thread; MariaDB 0,9-1,2 GB (buffer pool ikut naik).


9. CARA MENGULANG
------------------------------------------------------------------------------------------------

  1. Siapkan database KOSONG: php artisan migrate --force; php artisan db:seed --class=RoleSeeder.
  2. mysql < deploy/loadtest/seed.sql (ganti __HASH__ dengan hash bcrypt cost 12 untuk "Perf@2026");
     buat token Sanctum: INSERT ... SELECT seq, 'App\\Models\\User', seq, 'perf', SHA2(CONCAT('perf',
     seq),256) ... (token = "{id}|perf{id}"); letakkan satu PDF uji 5 MB di storage/app/private/
     ebooks/perf/sample.pdf; jalankan seed3.sql (komentar, aturan buka, pengaturan royalti).
  3. Produksi-like: APP_DEBUG=false, config:cache, route:cache, OPcache, PHP-FPM 48 worker.
  4. node deploy/loadtest/loadtest.mjs --base http://HOST --duration 60 --warmup 10 --book 4
        --press 0.04 --admin 0.1 --think 0.1      (naikkan --book sampai CPU 60%).
  5. Profil query per request: php deploy/loadtest/qprofile.php (sesuaikan jalur).
  6. Bandingkan ms-CPU/request dengan bagian 6 lalu hitung ulang tabel kapasitas.
  JANGAN jalankan terhadap database produksi: skrip menulis ribuan baris dan token.
