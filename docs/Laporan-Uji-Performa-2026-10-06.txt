1. RINGKASAN
------------------------------------------------------------------------------------------------

  Dengan data saat ini (12 user, 17 buku, 29 pesanan) sistem CEPAT: hampir semua endpoint
  diproses di bawah 100 ms. Namun sistem BELUM SIAP TUMBUH. Pada data simulasi 300x lebih besar
  (3.600 user, 5.100 buku, 8.700 pesanan, 3.900 naskah):

  +----------------------------------------------+----------------+------------------------------+
  | Temuan                                       | Tingkat        | Dampak                       |
  +----------------------------------------------+----------------+------------------------------+
  | P1 Daftar tanpa pagination (katalog buku,    | KRITIS         | /books 6,6 dtk & 13 MB JSON; |
  |    semua daftar admin, Book Chapter)         |                | admin 7-23 dtk per halaman   |
  | P2 Query N+1 (relasi dimuat satu per satu)   | KRITIS         | hingga 16.543 query/request  |
  | P3 Memori per request > batas PHP            | KRITIS         | /admin/books ERROR 500       |
  |                                              |                | (butuh ~250 MB, batas 256 MB)|
  | P4 Sampul buku tidak diperkecil              | TINGGI         | Beranda memuat ~11 MB gambar |
  | P5 Semua halaman dalam 1 berkas JavaScript   | SEDANG         | 1,33 MB (368 KB gzip) untuk  |
  |    (tanpa code-splitting)                    |                | setiap pengunjung            |
  | P6 /about diminta ulang di setiap halaman,   | RENDAH         | 1 request tambahan per       |
  |    9 request API di beranda                  |                | halaman                      |
  +----------------------------------------------+----------------+------------------------------+

  Kesimpulan: aman untuk peluncuran dengan volume data sekarang, tetapi P1-P3 harus diperbaiki
  sebelum data mencapai ratusan buku/pesanan; P4 sebaiknya segera karena terasa di HP sekarang.

4. AKAR MASALAH (U3)
------------------------------------------------------------------------------------------------

  4.1 N+1 dari atribut tambahan model ($appends)
      Atribut dihitung untuk SETIAP baris saat diubah ke JSON dan memuat relasinya satu-satu:
      - Book::editor_name            -> manuscript -> editor, ownerEditor
      - BookChapter::effective_price, effective_discount -> book;  slot_status -> manuscript
      Hasil: /admin/books = 7.800x "select books where id = ?" + 6.000x "select users ...".
      Solusi: eager load (with('chapters.book', 'manuscript.editor', 'ownerEditor')) atau
      setRelation induk ke anak; aktifkan Model::preventLazyLoading() di lingkungan dev/tes
      agar N+1 baru langsung ketahuan.

  4.2 N+1 di layanan agregat
      - Ringkasan (dashboard/summary) & /admin/hki: per pesanan memuat order, manuscripts,
        manuscript_authors, users; plus 3.300x "select includes_hki from finance_details".
      - /admin/finance/packages: 3.600x manuscripts + 3.000x books per pesanan.
      - /admin/isbn-applications: 1.800x users + 900x revisions per surat.
      - /admin/vouchers & voucher-grants: 3 query nama target per voucher.
      Solusi: muat sekali dengan whereIn/with lalu petakan di memori; untuk angka Ringkasan
      gunakan COUNT/SUM di database, bukan memuat semua baris.

  4.3 Tanpa pagination
      Katalog publik, Book Chapter, artikel, event, direktori penulis/editor dan hampir semua
      daftar admin mengembalikan SELURUH baris. Laporan keuangan memuat semua pesanan lunas
      beserta item ke memori (FinanceService::paidOrders).
      Solusi: paginate (mis. 20-50 per halaman) + filter/pencarian di server; frontend memakai
      "muat lebih banyak"/nomor halaman. Beranda cukup meminta N buku terbaru (?limit=8).
      Untuk keuangan: agregasi SQL per periode, atau tabel ringkasan bulanan.

  4.4 Biaya per request
      Server dev: ~250-350 ms per request walau proses aplikasi hanya 3 ms, karena tanpa
      OPcache, tanpa config/route cache, APP_DEBUG aktif, dan koneksi PostgreSQL lokal di
      Windows ~40 ms. Mode produksi + MariaDB: ~25-35 ms per request ringan.

       ab -n 500 -c 20 -H "Accept: application/json" https://DOMAIN/api/v1/books/<slug>
     Lakukan di luar jam ramai; jangan ke endpoint yang menulis data.
